# Rank-`g` Poisson summation: what's needed, what exists

Notes on the missing analytic ingredient behind the `S_g` Siegel modular transformation law
(`ZetaFunctions/SiegelModular.lean`, `section ThetaTransformSMatrix`) and the Epstein zeta
functional equation (`ZetaFunctions/EpsteinZeta.lean`), and how the two connect.

## Mathlib's Poisson summation is rank-1 only

- `Mathlib.Analysis.Fourier.PoissonSummation`: `Real.tsum_eq_tsum_fourier` and its corollaries
  (`_of_rpow_decay`, `SchwartzMap.tsum_eq_tsum_fourier`) are all `∑' (n:ℤ), f(x+n) = ∑' (n:ℤ), 𝓕f n · e(nx)`
  — one variable.
- `Mathlib.Analysis.SpecialFunctions.Gaussian.PoissonSummation`: `Complex.tsum_exp_neg_quadratic` /
  `Complex.tsum_exp_neg_mul_int_sq` — the Jacobi-theta corollary, but with a *scalar* `a : ℂ`, not a
  matrix.
- `Mathlib.Analysis.SpecialFunctions.Gaussian.FourierTransform`: `fourier_gaussian_innerProductSpace`,
  `integral_cexp_neg_mul_sq_norm_add_of_euclideanSpace` — genuinely multivariate, but only for
  *isotropic* Gaussians `exp(-b‖v‖²)`. Getting to an arbitrary PosDef matrix needs a linear
  change-of-variables (Cholesky-type) argument composed on top; not done anywhere.
- `Mathlib.Analysis.Fourier.AddCircleMulti`: multivariate Fourier *series* on the `d`-torus, the
  structural tool `Real.fourierCoeff_tsum_comp_add` builds on for `d=1` — no theorem chains it up to
  a `d`-dimensional Poisson summation formula.
- No rank-`g` (lattice) Poisson summation formula exists anywhere in Mathlib.

`ThetaFunctions.lean` imports both `PoissonSummation` files but (checked by grep) never calls
`Real.tsum_eq_tsum_fourier`/`Complex.tsum_exp_neg_quadratic` anywhere. The one thing actually used

## The target identity for `S_g` (SiegelModular.lean)

Recorded as a `/-! -/` comment at the top of `section ThetaTransformSMatrix`
(SiegelModular.lean:1878). Derived by treating the desired fact as the direct matrix
generalization of `Complex.tsum_exp_neg_quadratic`:

```
∑' (n : Fin g → ℤ), exp (-π * ∑ i, ∑ j, A i j * n i * n j + 2 * π * ∑ i, b i * n i) =
  1 / (Matrix.det A) ^ (1/2 : ℂ) *
    ∑' (n : Fin g → ℤ), exp (-π * ∑ i, ∑ j, A⁻¹ i j * (n i + I * b i) * (n j + I * b j))
```

for `A : Matrix (Fin g) (Fin g) ℂ` symmetric, `Re A ≻ 0`, `b : Fin g → ℂ`. Applying with
`A := -I • τ.toMatrix` (`Re A = gramMatrixReal τ.Q_Im ≻ 0` automatically, since `τ` is a
`SiegelUpperHalfSpace`) and `b := I • w` where `w i := z (Pi.single i 1)`, then completing the
square with `M := siegelMatrixAction Smatrix τ.toMatrix = -τ.toMatrix⁻¹`
(`siegelMatrixAction_Smatrix`), gives:

```
theta_fun old_thetaable z =
  1 / ((-I) ^ g * τ.toMatrix.det) ^ (1/2 : ℂ) *
    Complex.exp (-π * I * ∑ i, ∑ j, τ.toMatrix⁻¹ i j * w i * w j) *
    theta_fun (RiemannThetaAble_siegelSMul hg (Sp2gR.Smatrix (R := ℤ) (g := g)) old_thetaable) z'
```

with `z' n = ∑ i, ∑ j, τ.toMatrix⁻¹ i j * w j * n i` (i.e. `z' = τ⁻¹ w`). This is *not* a corollary
of the summand-level lemmas already proved (`x_summand_quadratic_after_Smatrix`,
`theta_summand_after_Smatrix`) — those only rewrite the exponent term-by-term; the identity above
needs the genuine reindexing/resummation, which is exactly the missing rank-`g` Poisson summation
formula.

**Decay side-conditions are already free.** `siegelMatrixAction_im_posDef` (SiegelModular.lean:654)
proves `Im(M•Z)` PosDef for *any* `M : Sp2gR g`, and it's baked into `siegelSMul`'s own
construction (`hQIm := siegelMatrixAction_im_posDef M τ`, line 750). So `siegelSMul Smatrix τ` is,
by construction, already a bona fide `SiegelUpperHalfSpace`, meaning `RiemannThetaAble`'s
`gaussianThetaConst`/`gaussianThetaRate`/`gaussianVPolyDecay` machinery (ThetaFunctions.lean
~1103–1330) applies unchanged on *both* sides of the identity — no new summability argument needed,
only the Fourier-duality identity itself.

## `Sp(2g,ℤ)` generation and where `S_g` sits in it

Classical fact (Klingen, *Introductory Lectures on Siegel Modular Forms*, Ch. I):
`Sp(2g,ℤ)` is generated by `T_B = [[I,B],[0,I]]` (`B` symmetric integral) and
`S = [[0,-I],[I,0]]`. `GL(g,ℤ)` block matrices (`Sp2gR.GLmatrix`) are not logically independent —
representable as words in `T_B`/`S` — but are kept as a primitively-proved generator in this
project anyway since their transformation law is termwise/free (no analysis needed), unlike `T`/`S`.

Mathlib already has the abstract rank-1 generation fact:
`SpecialLinearGroup.SL2Z_generators : closure {S, T} = ⊤`
(`Mathlib.LinearAlgebra.Matrix.FixedDetMatrices`).

`Sp2gR.SL2blockHom B hB hBdet : SL(2,R) →* Sp2gR g` (Sp2gR.lean:394, classified by
`Sp2gR.SL2blockHom_classification`) is a genuine `MonoidHom`, so `SL2Z_generators` pushes forward
via `MonoidHom.map_closure` to generate `(SL2blockHom B).range` for free — no new group theory
needed for elements in that image.

Checking blocks: `Sp2gR.Smatrix` has `(A,B,C,D) = (0,-1,1,0)` (Sp2gR.lean:222-232).
`SL2blockHom B` at `SL2rotation = [[0,1],[-1,0]]` gives `(0, B, -B⁻¹, 0)`; at `B = 1` that's
`(0,1,-1,0) = -Smatrix`, and `-M` acts identically to `M` on `SiegelUpperHalfSpace g` (central
sign). So `Sp2gR.Smatrix` literally *is* `Sp2gR.SL2blockHom 1 hI hIdet` applied to the abstract
`SL(2,ℤ)` rotation generator.

**But this factors the group element, not the analysis.** `SL2blockHom B`'s action on a *generic*
`τ` is still the full `g×g` transform (at `B=1`, the full inversion `τ ↦ -τ⁻¹`, mixing all `g`
coordinates) — so this doesn't shrink the Poisson-summation content needed for a generic `τ`.

**Where it does shrink the target**: restrict to the diagonal locus `τ = t • B` (the orbit of
`SL2blockHom B`) — exactly the slice `epsteinGaussianThetaAble` already isolates. There the needed
transformation law under `t ↦ -1/t` is the *Epstein zeta functional equation* for the lattice form
`B`: real-valued, no complex shift, and it plugs into machinery already built (see below).

## Epstein zeta functional equation: gap analysis

`EpsteinZeta.lean` (512 lines) + `ThetaFunctions.lean`'s `EpsteinGaussianTheta`/
`EpsteinThetaZetaMellin` sections already prove the classical "first half" of Riemann's argument:

- `epsteinZetaAble hn q hq : ZetaAbleQuadraticForm` (EpsteinZeta.lean:482) —
  `ζ_q(s) = ∑'_{x≠0} q(x)^(-s)`, `Re(s) > n/2`, `q : QuadraticMap ℤ (Fin n → ℤ) ℤ` PosDef.
- `epsteinGaussianThetaAble hn q hq τ hτ` (ThetaFunctions.lean:1427) — the scalar slice `θ(z; τq)`.
- `epstein_zeta_eq_theta_mellin'` (ThetaFunctions.lean:1675) — **already proved**:
  `Γ(s) π⁻ˢ ζ_q(s) = ∫₀^∞ tˢ⁻¹ (θ_q(it) - 1) dt`.

Three pieces still missing to reach the functional equation itself:

1. **The dual form `q*`.** Not defined anywhere. `q*(x) := x^T (gramMatrix q)⁻¹ x`, real-valued
   (generally irrational, not integral). Typechecks fine against the existing generic
   `ZetaAbleQuadraticForm {M S} [...] where q : QuadraticMap R M S` (already generic in `S`):
   `q* : QuadraticMap ℤ (Fin n → ℤ) ℝ` is valid (`ℝ` is a `ℤ`-module). Would need an
   `epsteinZetaAbleDual`-style instance-builder alongside `epsteinZetaAble`, reusing
   `gramQuadraticMap`/`posDef_lower_bound` but skipping the ℚ-density transfer step (real-valued
   from the start). `IsUnit (gramMatrix q).det` already available from `gramMatrix_det_ne_zero`
   (anisotropy of PosDef `q`).

2. **The real, shift-free theta transformation law** — the actual missing analytic content:
   `θ_q(i/t) = t^(n/2) · (det (gramMatrix q))^(-1/2) · θ_{q*}(it)`.
   This is the narrowest member of the "rank-`g` Poisson summation" family: real `t > 0`, no shift
   (`z = 0`) — i.e. Mathlib's `Real.tsum_exp_neg_mul_int_sq` generalized from scalar `a : ℝ` to a
   PosDef matrix `A = gramMatrix q`. The natural first target to actually formalize.
   Open question: whether this reduces cleanly to the scalar case via diagonalizing `A`
   (`A = UᵀDU`) — the obstruction is that an arbitrary orthogonal change of basis does not
   preserve the lattice `ℤⁿ`, so naive diagonalization doesn't immediately work; may still need
   the genuinely multivariate `fourier_gaussian_innerProductSpace` + a real multivariate Poisson
   summation, same underlying gap as the `S_g` case, just without the complex shift.

3. **The classical gluing argument**: split `∫₀^∞ = ∫₀^1 + ∫₁^∞`, substitute `t ↦ 1/u` in the
   `(0,1)` piece using (2), recombine. Also where meromorphic continuation and the simple pole of
   `ζ_q(s)` at `s = n/2` (with explicit residue) fall out — the "`-1`" term integrated against
   `t^{s-1}` over `(0,1)` after substitution produces the pole. `θ_q(it) - 1 → 0` exponentially as
   `t → ∞` is already available via `gaussianThetaRate`/`gaussianVPolyDecay`.

## Progress: `PoissonSummation.lean` (2026-07-15)

The statement is now filled in and under active proof. Two findings/decisions so far:

**Branch-cut bug found and fixed.** The naive `A.det ^ (1/2 : ℂ)` (`Complex.cpow`, principal
branch) is only a valid square root for `g ≤ 2` — for symmetric `A` with `Re A ≻ 0`, writing
`A = R(I + iS)R` (`R` = PosDef square root of `Re A`, `S` real symmetric, via congruence) gives
`arg(A.det) = ∑ arg(1 + iλₖ)` over eigenvalues `λₖ` of `S`, each term strictly inside `(-π/2,π/2)`.
For `g ≥ 3` this sum can exceed `π` (explicit counterexample: `A = (1+it)•I₃`, crosses the branch
cut at `t = √3` where `A.det = -8`), so `cpow` jumps by a sign relative to the true continuous
square root while the LHS sum is manifestly continuous — the naive statement is false there, not
just hard. Fixed by replacing `A.det ^ (1/2:ℂ)` with `pivotSqrt g A`: the product of principal-branch
square roots of the pivots of repeated one-coordinate Schur complementation (`schurStepLast`), a
"plain-transpose LDL-decomposition" (distinct from Mathlib's `Mathlib.Analysis.Matrix.LDL`, which
is for `IsHermitian`/`Mᴴ`, not our `IsSymm`/`Mᵀ`). Each pivot has `Re > 0` individually (once
`schurStepLast_re_posDef` below is proved), so each factor's `cpow` is branch-safe by the `g=1`
argument, and `pivotSqrt_sq` (proved) confirms the product squares to `A.det`.

**Proof strategy: induction on `g` via one-coordinate Schur complement**, peeling off the last
coordinate (`Fin.last g` / `Fin.castSucc`) each step, since Mathlib has *no* multivariate Poisson
summation or lattice/fundamental-domain Fourier machinery to build on (checked: `AddCircleMulti`,
`Fourier/PoissonSummation.lean` — genuinely ℝ/ℤ-only; `Analysis.Matrix.LDL` is Hermitian-only).
Current file state (`ZetaFunctions/PoissonSummation.lean`):

- `schurStepLast`, `pivotSqrt` — defined, no gaps.
- `schurStepLast_isSymm` — proved.
- `schurStepLast_re_posDef` — **proved** (2026-07-15), *not* via `siegelMatrixAction_im_posDef`
  (constructing the needed symplectic block-embedding element turned out to be more work than a
  direct argument). Elementary self-contained proof: for a real test vector `x` on the Schur
  complement, extend to `y := Fin.snoc x t : Fin (g+1) → ℝ` with `t := -(∑ v i * x i).re / a.re`
  (`v` = eliminated column, `a` = pivot) and apply `Re A ≻ 0` directly to `y`; this gives a strict
  real inequality `xᵀRe(A₁₁)x > Re(c)²/Re(a)` (`c := ∑ v i * x i : ℂ`) that dominates the actual
  complex quantity `Re(c²/a)` appearing in the Schur complement's quadratic form, via the perfect-
  square identity `Re(c)²/Re(a) - Re(c²/a) = (Re(c)Im(a) - Im(c)Re(a))² / (Re(a)·|a|²) ≥ 0`
  (isolated as standalone lemma `re_sq_div_le`). No calculus/argmin reasoning needed — `t` is
  plugged in directly at its closed form, sidestepping any minimization tactic.
- `pivotSqrt_sq (g A) (hA) (hRe) : pivotSqrt g A ^ 2 = A.det` — proved, modulo the one sorry below.
- `det_eq_pivot_mul_det_schurStepLast` — **proved** (2026-07-15) via exactly the sketched route:
  reindex `Fin (g+1) ≃ Fin g ⊕ Fin 1` via `finSumFinEquiv`, show
  `A.submatrix e e = Matrix.fromBlocks A₁₁ A₁₂ A₂₁ A₂₂` with blocks matching `schurStepLast`'s
  pieces (`ext (i|i) (j|j) <;> simp [...]`, with `Fin.eq_zero` — bare, unapplied — as the simp
  lemma that collapses `Fin 1` variables to `0` uniformly across all four `Sum` cases; passing it
  pre-applied as `Fin.eq_zero i` breaks in the cases where `i : Fin g`), then
  `Matrix.det_submatrix_equiv_self` + `Matrix.det_fromBlocks₂₂`. One gotcha:
  `Matrix.det_fromBlocks₂₂` is stated with `⅟D` (`invOf`), not `D⁻¹` (`Matrix.inv`/nonsing inv) —
  needed `Matrix.invOf_eq_nonsing_inv` to bridge to the `A₂₂⁻¹` used when constructing the 1×1
  inverse by hand.
- `tsum_exp_neg_quadratic_matrix` itself (**sorry**, the only remaining gap in the file) — the
  induction is set up (`induction g`) with the `g = 0` base case **proved** (`tsum_fin_zero_eq`

  2. **Apply `Complex.tsum_exp_neg_quadratic`** to the inner `k`-sum (using `quadratic_exponent_split`

     internally), but produces a *new* dual sum over `m : ℤ` whose shift `β(n') := b(last) - ∑ v_i n'_i`
     depends on `n'`.
  3. **Complete the square a second time**: expanding `exp(-π/a·(m + I·β(n'))²)` introduces an
     `L(n')² = (∑ v_i n'_i)²` term that combines with `-π·Q'(n')` into exactly `-π·Q''(n')` where
     `Q''` is `schurStepLast A`'s quadratic form (hand-verified on paper, not yet in Lean) — this is
     where `schurStepLast`'s definition is *used*, not just its positivity/determinant properties.
  4. **Block-inverse Schur identity for `A⁻¹`** (not just `A.det`, which `det_eq_pivot_mul_det_schurStepLast`
     already handles) — **proved** as `matrix_inv_blocks` (2026-07-15): all four block entries of
     `A⁻¹` in terms of `(schurStepLast A)⁻¹`, `v` (the eliminated column), and the pivot `a`. Same
     `finSumFinEquiv`/`fromBlocks` scaffolding as `det_eq_pivot_mul_det_schurStepLast`, targeting
     `Matrix.invOf_fromBlocks₂₂_eq` (`LinearAlgebra/Matrix/SchurComplement.lean`) instead of
     `det_fromBlocks₂₂`. Two new snags, both resolved:
     - **Dependent-instance rewrite trap**: converting `⅟(A₁₁ - A₁₂⅟A₂₂A₂₁) → (schurStepLast A)⁻¹`
       cannot be done as a single `rw [hschur]` while the term is still in `⅟`-form (`Invertible.invOf`
       notation) — the base matrix `A₁₁ - A₁₂⅟A₂₂A₂₁` is an *index* of the dependent `Invertible`
       instance embedded in `⅟(...)`'s elaborated term, so rewriting it there hits Lean's classic
       "motive is not type correct" error (same failure class as this project's
       [[feedback_eqtohom_liftcycles_rewriting]] note, just for `Invertible.invOf` instead of
       `eqToHom`). Fix: convert *all* `⅟X → X⁻¹` (`Matrix.invOf_eq_nonsing_inv`, plain `Matrix.inv`,
       not tied to a specific instance in its type) *first*, then rewrite the now-untyped-in-that-way
       base via `hschur` — never rewrite under a live `⅟`.
     - Extracting individual entries needs `Finset.mul_sum`/`Finset.sum_mul` to pull constants in/out
       of sums before `ring` can close (as elsewhere in this file, `ring` treats each distinct
       `Finset.sum` as an opaque atom) — and when a sum is wrapped in an outer `-` or multiplied by a
       trailing constant, `rw [← Finset.mul_sum]` often can't unify because left-associativity groups
       the "constant" together with a bound-variable-dependent factor first. More robust fix used
       throughout: push `-`/the trailing constant *into* the sum on both sides first
       (`neg_mul`/`Finset.sum_mul`), then close termwise via `Finset.sum_congr rfl (fun _ _ => by ring)`,
       rather than trying to factor constants back out.
  5. **Reassemble**: combine steps 1–4 with the induction hypothesis (applied to `schurStepLast A`
     and the `m`-dependent shift `b'(m)`) and match prefactors via `pivotSqrt`'s recursive definition
     (`pivotSqrt (g+1) A = a^(1/2) · pivotSqrt g (schurStepLast A)`, already how `pivotSqrt` unfolds).
     Not started — the by-hand derivation (see below) is fully checked, but not yet in Lean.

  **All the algebra is now in place** (`quadratic_exponent_split` for the LHS, `matrix_inv_blocks` for
  the RHS); step 1 (summability, needed for `tsum` Fubini) is the one piece needing genuinely new
  infrastructure, and step 5 (wiring everything together with `Complex.tsum_exp_neg_quadratic`) is

  **Hand-verified derivation** (not yet formalized, but cross-checked and self-consistent — see

  splitting `n = Fin.snoc n' k` and applying `Complex.tsum_exp_neg_quadratic` to the `k`-sum produces
  a dual variable `m` and a shift `β(n') := b_{last} - ∑ v_i n'_i`. Expanding
  `exp(-π/a·(m+Iβ(n'))²)` and collecting the `n'`-quadratic part gives exactly `-π·Q''(n')` with

  just a convenient one); the `n'`-linear part gives a new `m`-dependent shift
  `b'(m)_i := b_i + (Im - b_{last})v_i/a`; and the leftover pure-`m` term `C(m) := -π/a·(m+Ib_{last})²`

  contributes when substituted into the target RHS exponent — i.e. the two independently-derived
  sides (LHS via double square-completion, RHS via the block-inverse formula) match termwise. This
  cross-check is strong evidence the overall statement and strategy are correct.
